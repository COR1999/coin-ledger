## Decisions
- **Idempotency key must include a time-varying field, not just the in-memory proposal id** (Phase 6, 2026-10-01) — `InMemoryPaymentProposalRepository`'s counter resets to 1 on every dev-server restart (`lib/repositories/in-memory.ts`), so `deterministicIdempotencyKey(\`proposal-${proposalId}\`)` produced the exact same key for, e.g., every process's 2nd-ever proposal — Circle's API correctly treated repeats as retries and replayed an old tx instead of executing a new payment. Fixed by seeding with `proposal-${proposalId}-${proposal.createdAt}` instead — still deterministic for genuine retries of the same in-memory proposal within one process, unique across restarts. Worth keeping in mind if proposal ids ever become persistent/database-backed: the fix becomes unnecessary (ids would no longer repeat) but is harmless either way.
- **Switched the agent model from `gemini-3.5-flash` to `gemini-3.6-flash` to route around an exhausted free-tier daily quota** (Phase 6, 2026-10-01) — mid-way through running the three demo stories, `gemini-3.5-flash` hit Google's free-tier cap (`GenerateRequestsPerDayPerProjectPerModel-FreeTier`, 20 requests/day, resets at Pacific midnight — confirmed by the quota error's own `quotaDimensions.model` field, i.e. scoped per model name). Rather than block for up to 24h, called `GET /v1beta/models?key=...` on the same key, found several sibling Gemini-3 models, and confirmed by direct API call that `gemini-3.5-flash-lite`, `gemini-3.6-flash`, and `gemini-3.7-flash` all had untouched quota (`gemini-2.5-flash-lite` 404s — "no longer available to new users" — and `gemini-flash-latest` was 503 at the time). Picked `gemini-3.6-flash`: same family as the already-tested `gemini-3.5-flash`, so the existing `thoughtSignature`-echoing and retry logic in `lib/agent/agent.ts` needed no changes. **This was a same-session stop-gap, not a considered model evaluation** — no comparison of quality/latency/cost against `gemini-3.5-flash` was done. Revisit once either model's quota resets or the key moves to a paid tier; don't treat `gemini-3.6-flash` as the settled choice without that follow-up.
- **Aomi deprioritized in favor of Circle developer-controlled wallets for execution** (Phase 4 research, 2026-09-30) — read Aomi's own docs at aomi.dev directly (not guessed). Finding: Aomi's no-prompt automatic signing (`auto` wallet policy) requires a **live delegated grant**, and the docs' own glossary defines that as *"a revocable authorization that lets an embedded wallet provider such as Privy or Para sign without a prompt for each transaction"* — Circle is not mentioned anywhere in Aomi's docs. Aomi's backend ("App") explicitly cannot itself hold signing power: *"Connecting a wallet does not grant unattended signing"*; App credentials only scope which App a caller may use, separate from wallet signing authority. Since our execution path already gates on human approval upstream (policy engine + `/approvals`) before reaching execution, a Privy/Para wallet-connect + delegation flow would duplicate that gate and add real hackathon-time integration surface (wallet-connect UI, embedded-wallet onboarding, grant setup) for no architectural benefit. **Decision:** use Circle developer-controlled wallets for the execution step — created/controlled entirely server-side via API, no end-user wallet-connect flow, matches the existing `execute.ts` design directly. Aomi deprioritized to an optional future add-on (e.g. a chat-based propose/simulate surface) rather than the execution path itself. Still genuinely unconfirmed even after reading the docs directly (would need asking Aomi, not guessable): whether the one-time Privy/Para grant setup could be done as a business-only step with no real end-customer — only relevant if Aomi is revisited later.
- **Agent runs on Google Gemini, not Anthropic** (Phase 3) — the user has a free-tier Google API key, not an Anthropic one. `@google/genai`, model `gemini-3.5-flash`. `gemini-2.5-flash` returns 404 for newly-created keys ("no longer available to new users") and `gemini-3.8-flash` was consistently 503 (overloaded) during testing; `gemini-3.5-flash` was available and responsive. The `executeTool` dispatch is provider-agnostic — only the tool-definition shape and the request/response loop are Gemini-specific, so switching providers later is contained to `lib/agent/agent.ts` + the `toolDefinitions` array. (2026-09-30)
- **Gemini 3 requires echoing the model turn verbatim** (Phase 3) — function-call parts carry a `thoughtSignature`; reconstructing the assistant turn from `response.functionCalls` drops it and the next request 400s ("Function call is missing a thought_signature"). Fix: push `response.candidates[0].content` back unchanged. Also added exponential-backoff retry for transient 503/429 (free tier under load). (2026-09-30)
- **Repositories are a process-wide singleton** (`lib/repositories/singleton.ts`, Phase 2) — the in-memory factory re-seeds on every call, so owner policy edits would not survive across requests. One instance per server process (stashed on `globalThis` to survive dev hot-reload) keeps edits visible until restart; a database behind the same interfaces would replace it without touching callers. (2026-09-30)
- **Role is a cookie, enforced server-side** (Phase 2) — no real auth; the role switcher posts a known actor id to a server action that sets an httpOnly cookie. Every authorization check (e.g. policy editing) re-reads the cookie via `getCurrentActor()` and re-checks `canEditPolicies` against the live policy — never a client flag. Verified: Liam's `/settings` is read-only and has no submit path. (2026-09-30)
- **Forecast chart is a dependency-free inline SVG** (Phase 2) — server-rendered, accessible (role="img" summary + visually-hidden data table), with a dashed minimum-reserve reference line. Avoids pulling in a chart library for one chart, per the "minimal dependencies" standard. (2026-09-30)
- **Only numeric limits are editable in policy settings** (Phase 2) — role capabilities (who may approve, employee supplier restriction, who may edit policies) and the owner's null daily limit are structural and not exposed, so an owner cannot lock themselves out. The owner's approval limit tracks their single-payment limit. Zod also enforces owner ≥ accountant ≥ employee single-payment ordering. (2026-09-30)
- **Disabled Next.js 16 `agentRules`** (`next.config.ts`, Phase 2) — `next dev` was appending a "nextjs-agent-rules" block to our authored `CLAUDE.md` on every run. Set `agentRules: false` and reverted the file so the project's instructions stay pristine. (2026-09-30)
- **Employee daily limit only caps self-authorizable payments** (Phase 1). A payment within the actor's single-payment limit counts against their daily cap; a larger payment escalates to approval instead, where a different authority answers, so the requester's daily cap does not reject it. This reconciles scenario 3 (Liam €2,400 → needs_approval) with scenario 9 (Liam €30 after €280 → rejected). Generalised to any role with a daily limit. (2026-09-30)
- **Policy reasons are collected, not short-circuited** (Phase 1) — a payment breaking several rules reports all applicable reasons; tests assert the documented reason is present, not that it is the only one. (2026-09-30)
- **Money is integer cents end to end** (`lib/money.ts`); decimal strings only at boundaries. `eur()` builder keeps float literals out of seed/policy data. (2026-09-30)
- **Balance stored on the business, not derived from transactions** (Phase 1) — seed gives the authoritative €18,420; the transaction history is illustrative for now, to be expanded in the dashboard phase. (2026-09-30)
